# Custom Reminder Messages: Free Text, Not Curated Voices

Pillie Plus gains a Custom Reminder Message perk that lets a subscriber replace the default reminder copy with their own free text. In v1 it covers the Due Action Reminder and the Auto-Reminder Retry — each with a custom title and body (four fields) — and excludes the Supply Reminder. It is additive: free users keep every existing reminder setting (Reminder Time, Auto-Reminder Interval, Auto-Reminder Retry Limit, Supply thresholds). The perk is listed as a supporting comparison row on the Soft Onboarding Paywall and the Settings paywall, which share `SoftPaywallContent.default`; Plus App Blocking remains the differentiator and the paywall hero.

The significant decision is that the message is **free text typed by the user**, not a selection from a set of Pillie-authored voice or tone packs. This is surprising against the rest of the codebase: Pillie's domain language is obsessively careful never to imply medical protection, contraceptive efficacy, or health-risk reduction (see `Reminder Plan`, `Pill Protection Plan`, and the proof screens in ADR 0003, which forbid medical claims). A feature that lets users type arbitrary notification text appears, at first glance, to hand them a way to author exactly the kind of copy the rest of the product polices.

We accept free text anyway because a Custom Reminder Message is categorically different from Pillie-authored copy. It is the user's own private, on-device reminder to themselves: it is never shown to anyone else, never leaves the device, and is not user-generated content surfaced to other users. Pillie's medical-claims rules govern *Pillie's* voice in marketing and product copy; they do not govern what a user privately writes to themselves. There is therefore no moderation surface and no App Store UGC concern, and the curated-voice option's main advantage — guaranteeing compliant copy — protects against a risk that does not exist here. The trade-offs we explicitly accept in exchange for the simpler, more personal free-text model: copy can read method-wrong after a contraception method change (a Custom Reminder Message is a Personalization Setting, persists across method changes like Reminder Time, and is the user's to edit), and there is no localization or templating of the user's words.

The constraints that *do* matter are display length and graceful fallback, and these are enforced structurally rather than by moderation. Length is prevented at input with hard per-field character caps (title 50, body 150) shown via a live counter, so the editor is WYSIWYG and the user always sees exactly what will fire; a defensive clamp at build time is a safety net, not the UX. Any field left blank falls back independently to the existing default method-aware copy, so clearing a field can never produce an empty notification.

The Plus entitlement is enforced at the build layer, in `NotificationManager.buildReminderRequests`, not only in the editor UI. When `isPlus` is false the custom strings are ignored and defaults are used, while the typed strings are retained in storage. This makes the build path the single source of truth: the same check governs both whether the editor is offered (the existing `Blocked Apps` gating pattern) and whether custom text actually fires, so the perk cannot leak to a lapsed subscriber. Enforcement is eventual — a notification already queued keeps its custom text until the next reschedule (mark-taken, settings change, or launch) — which is acceptable for flavor copy that has no functional or schedule impact. Retaining the strings on lapse is deliberate: a user who resubscribes gets their personalization back with zero friction.

The text is private routine content and is never sent as Product Analytics Telemetry. Only coarse funnel and adoption signals are captured: upsell viewed, upgrade tapped, editor opened, and a boolean per field for whether it is customized. The words themselves stay on the device, consistent with the on-device promise built into the term.
